## 1. Phase Schedule

The MVP adds 6 new capability areas to the PoC codebase. Phases are ordered by **risk** (highest first) and **dependency** (infrastructure before features). The plan is optimized for a **single developer** with per-phase contract test gates and `/simplify` passes per the pipeline improvements ADR.

### Phase Overview

| Phase | Name | Duration | Task Count | Risk | Key ADRs |
|-------|------|----------|------------|------|----------|
| 0 | CDK Infrastructure & Cognito | 2–3 days | 8 | **High** | ADR-008, ADR-007 |
| 1 | Authentication Backend | 2 days | 7 | **High** | ADR-007 |
| 2 | Authentication Frontend | 2 days | 7 | **Medium** | ADR-007 |
| 3 | Enhanced AI Chatbot | 2 days | 7 | **Medium** | ADR-009 |
| 4 | Image Processing Pipeline | 1–2 days | 5 | **Low** | — |
| 5 | Desktop Responsive Layout | 1–2 days | 6 | **Low** | — |
| 6 | Integration, Polish & Deploy | 2–3 days | 8 | **Medium** | Pipeline ADR |
| **Total** | | **~13–17 days** | **48 tasks** | | |

### Dependency DAG

```
Phase 0 (CDK + Cognito)
  ├──→ Phase 1 (Auth Backend) ──→ Phase 2 (Auth Frontend)
  │                              │
  │                              ├──→ Phase 3 (AI Chatbot) [needs auth context for user-scoped conversations]
  │                              │
  ├──→ Phase 4 (Image Pipeline) [needs CDK for thumbnail Lambda; can run parallel to Phase 2-3]
  │
  └──→ Phase 5 (Desktop Responsive) [CSS-only; can start after Phase 0; no backend dependency]

All Phases ──→ Phase 6 (Integration & Deploy)
```

**Parallelism opportunities for solo developer**:
- Phase 4 (Image Pipeline) can interleave with Phase 3 (AI Chatbot) — different subsystems
- Phase 5 (Desktop Responsive) is CSS-only — can be done in any gap or parallel track
- Within phases, API and frontend tasks are often independent

## 4. Implementation Strategy

### Pipeline Flow (per MVP Pipeline ADR)

```
Per-phase loop:
  implement(Phase N)
    → contract tests (gate — all tests must pass)
    → /simplify (if > 200 lines changed)
    → commit
    → Phase N+1

After all phases:
  → test (full suite)
  → review → remediate
  → deploy
    → verify (checklist)
    → issue-create (any findings)
    → [fix loop]: issue → branch → Sonnet fix → Opus review → merge
```

### Git Branching

```
main (production-ready, explicit approval to merge)
  └── develop (integration branch)
        ├── feature/cdk-infrastructure        ← Phase 0
        ├── feature/auth-backend              ← Phase 1
        ├── feature/auth-frontend             ← Phase 2
        ├── feature/ai-chatbot-enhanced       ← Phase 3
        ├── feature/image-thumbnails          ← Phase 4
        ├── feature/desktop-responsive        ← Phase 5
        └── feature/mvp-integration           ← Phase 6
```

### Commit Cadence

- **One conventional commit per completed task** (e.g., `feat(cdk): define Cognito User Pool + App Client (T-CDK-07)`)
- **Intermediate commits** within large tasks encouraged
- **Commit message format**: `<type>(<scope>): <description> (T-XXXX-NN)`
  - Types: `feat`, `fix`, `docs`, `refactor`, `chore`, `test`
  - Scopes: `cdk`, `auth`, `api`, `frontend`, `ai`, `img`, `desktop`, `int`

### CDK Stack Resources

```
LitCropStack (single stack)
├── Cognito
│   ├── UserPool: litcrop-mvp-users
│   │     Email as username, password policy (8+ chars, mixed case + number)
│   │     ALLOW_USER_PASSWORD_AUTH, ALLOW_REFRESH_TOKEN_AUTH
│   │     Default email sender (50/day, sufficient for 1-10 users)
│   └── UserPoolClient: litcrop-mvp-web
│         No client secret (SPA client)
│         Token validity: access=1h, refresh=30d
│
├── Database
│   └── DynamoDB Table: litcrop-mvp
│         PK: pk (S), SK: sk (S)
│         GSI1: GSI1PK / GSI1SK (direct entity lookup)
│         GSI2: GSI2PK / GSI2SK (farm → plots query)
│         TTL attribute: ttl (for Conversation expiry)
│         Billing: On-Demand (pay-per-request)
│         RemovalPolicy: DESTROY (MVP only)
```

## 7. Risk Register

| # | Risk | Likelihood | Impact | Phase | Mitigation |
|---|------|-----------|--------|-------|------------|
| R-1 | CDK configuration complexity — many resources in first stack | Medium | High | 0 | Build incrementally: DynamoDB first, then S3, then Lambda. Validate `cdk deploy` after each resource group. |
| R-2 | Cognito Hosted UI customization limitations | Medium | Low | 0, 2 | Accept default UI for MVP. Custom login form is a Phase 2 option if needed. |
| R-3 | JWT Authorizer + CORS interaction issues | Medium | Medium | 0, 1 | Test preflight OPTIONS requests explicitly. Ensure CORS middleware runs before auth. |
| R-4 | Auth migration breaks existing PoC flows | Medium | High | 1 | Run full PoC contract tests at Phase 1 gate (with JWT added). Catch drift immediately. |
| R-5 | Multi-user data isolation gaps | Medium | **Critical** | 1 | Ownership middleware tested with negative cases (wrong user → 403). Security audit in Phase 6. |
| R-6 | Anthropic SDK bundle size affects Lambda cold start | Low | Low | 3 | Measured at ~150-200KB (ADR-009). ~15-20ms impact. Acceptable. |
| R-7 | Tool use loop adds latency / cost | Low | Medium | 3 | Cap max tool iterations (e.g., 3). Monitor response times. Use Haiku model. |
| R-8 | Sharp native dependencies in Lambda | Medium | Medium | 4 | Use Lambda layer for Sharp, or fall back to Jimp (pure JS). Test in CDK-deployed Lambda. |
| R-9 | S3 event → Lambda trigger latency | Low | Low | 4 | NFR-1.4 allows 10s. S3 events typically fire within 1-3s. |
| R-10 | Desktop CSS breaks mobile layout | Low | Medium | 5 | Mobile-first approach: desktop styles are additive `@media (min-width: 1024px)`. Test at 375px after every change. |
| R-11 | CDK deploy to production fails or creates orphaned resources | Low | High | 6 | CloudFormation rollback protects against partial deploys (NFR-5.3). `cdk diff` before every deploy. |
