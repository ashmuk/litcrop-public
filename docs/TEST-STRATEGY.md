## 1. Testing Philosophy (MVP)

### Why we test at MVP level

The MVP adds four high-risk surface areas on top of the validated PoC pipeline:

1. **Authentication & Authorization** — Every API endpoint now requires JWT validation and ownership enforcement. A single missing ownership check leaks another user's farm data (NFR-7.8). This is the highest-risk addition.
2. **AI Budget Controls** — DynamoDB atomic counters, threshold comparisons, daily resets, and 429 error paths. Pure business logic with financial consequences if broken (NFR-2.3).
3. **Token Budget Usage Endpoint** — New `GET /api/v1/usage` endpoint with its own Zod schema (`UsageResponseSchema`), not covered by PoC contract tests.
4. **Thumbnail Pipeline** — `thumbnail_url` field added to image responses; `ImageDetailResponseSchema` now includes `thumbnail_url`. The field must be present and correctly signed.

### What we DON'T test at MVP level

- **Cognito itself** — User Pool registration, email verification, and password flows are AWS-managed. We test our _integration_ with Cognito tokens, not Cognito's internal behavior.
- **CDK infrastructure correctness** — Validated by `cdk diff` + `cdk synth` + CDK-nag, not by Vitest. CDK tests are a Production-scope enhancement (FR-14.7 covers CDK-nag for security scanning).
- **Frontend pixel-perfection** — Desktop breakpoints (FR-12) are verified by manual browser inspection, not automated visual regression tests.
- **BYOK (Bring Your Own Key)** — Explicitly Production-only per REQUIREMENTS.md. Skip entirely.
- **Streaming SSE** — FR-9.8 is `Should` priority. If implemented, manual testing is sufficient for MVP.
- **100% branch coverage** — Still unnecessary. We target risk-proportional coverage, not coverage metrics.
- **E2E browser automation** — No Playwright/Cypress. Too expensive for MVP's 15-user validation target.
- **Load/performance testing** — NFR-1 targets are measured manually post-deploy.

### What carries forward from PoC (unchanged)

All PoC test coverage (§2–§10 of the original strategy) remains valid and required. The MVP strategy is _additive_ — it extends the PoC suite with new test areas. Nothing from the PoC is removed or demoted.

## 5. Coverage Plan — MVP Additions (By Risk Priority)

> PoC coverage (§5.1–§5.10 from original strategy) remains required and unchanged. This section covers **new MVP test areas only**.

### Critical (MUST test)

#### 5.11 Auth Middleware — JWT Extraction & User Context

File: `src/api/src/__tests__/middleware/auth.test.ts`

The auth middleware is the single point of trust for user identity. If it fails silently (e.g., returns a default user ID instead of rejecting), every ownership check downstream is bypassed.

| Test | Why Critical |
|------|-------------|
| Valid JWT → `c.get('user')` returns `{ sub, email }` | Happy path: all route handlers depend on this |
| Missing `Authorization` header → 401 `UNAUTHORIZED` | Unauthenticated access prevention |
| Malformed JWT (not base64, wrong segments) → 401 | Protects against crafted tokens |
| Expired JWT → 401 with "Token expired" message | Session expiry enforcement |
| JWT with `token_use: "id"` instead of `"access"` → 401 | Prevents ID token misuse (API Gateway also checks this) |
| JWT with wrong `iss` (different User Pool) → 401 | Cross-tenant isolation |
| Valid JWT but no `sub` claim → 401 | Malformed Cognito token; should never happen but must not crash |

**Implementation note**: Tests use `jsonwebtoken` to sign tokens with a test RSA key. The middleware should accept a configurable issuer/key for testing, or tests should mock the verification step to focus on claim extraction logic.

#### 5.12 Ownership Enforcement — User A Can't Access User B's Resources

File: `src/api/src/__tests__/middleware/ownership.test.ts`

This is the most security-critical test in the MVP. FR-1.7 requires that all farm data endpoints enforce per-user isolation. A failure here is a data breach.

| Test | Endpoint | Expected |
|------|----------|----------|
| User A requests User A's farm → 200 | `GET /farms/:farmId` | Farm returned |
| User A requests User B's farm → 404 (not 403!) | `GET /farms/:farmId` | `NOT_FOUND` — prevents resource enumeration |
| User A requests User B's plots → 404 | `GET /farms/:farmId/plots` | Ownership checked via farm lookup |
| User A requests User B's plot detail → 404 | `GET /plots/:plotId` | Ownership resolved: plot → bed → field → farm → user_id |
| User A requests User B's images → 404 | `GET /plots/:plotId/images` | Ownership resolved through plot chain |
| User A requests User B's image detail → 404 | `GET /images/:imageId` | Ownership resolved: image → plot → farm → user_id |
| User A tags User B's image → 404 | `POST /images/:imageId/tags` | Write path also checks ownership |
| User A requests User B's weather → 404 | `GET /farms/:farmId/weather` | Weather data is per-farm |
| User A updates User B's farm → 404 | `PATCH /farms/:farmId` | Write path also checks ownership |
| User A uploads image to User B's plot → 404 | `POST /plots/:plotId/images` | Upload requires ownership of parent plot's farm |
| User A chats with User B's farm context → 404 | `POST /chat` (with `farm_id`) | Chat tool use context is ownership-scoped |
| User A creates farm → `user_id` set to JWT sub | `POST /farms` | Farm creation uses JWT sub, not client-supplied user_id |

**Key assertion pattern**: Every ownership test must assert `404 NOT_FOUND` (not `403 FORBIDDEN`), per API-CONTRACTS.md §4b: "returns 404 to prevent resource enumeration."

#### 5.13 Budget Controls — Token Counting & Limits

File: `src/api/src/__tests__/services/budget.test.ts`

Budget controls protect against runaway LLM spending (ARCHITECTURE.md §AI Token Budget Controls). The logic involves DynamoDB atomic counters, threshold comparisons, and daily reset timing — all testable as pure logic with mocked DynamoDB.

| Test | Why Critical |
|------|-------------|
| `checkBudget()`: user under limit → `{ allowed: true }` | Happy path |
| `checkBudget()`: user at daily limit → `{ allowed: false, scope: 'user', reset_at }` | Per-user cap enforcement |
| `checkBudget()`: user under limit but global cap hit → `{ allowed: false, scope: 'global', reset_at }` | Global cap takes precedence |
| `incrementUsage()`: DynamoDB `UpdateCommand` with `ADD` expression | Verify atomic counter increment, not overwrite |
| `incrementUsage()`: new day (no existing record) → creates record with TTL | First-message-of-day path |
| `reset_at` calculation: always next midnight UTC | Time math correctness |
| Counter with TTL: TTL attribute set to midnight UTC + 24h | Ensures DynamoDB auto-cleanup |
| Conversation turn limit: 20 turns → `checkBudget()` returns `{ allowed: false }` | FR-9.10 enforcement |

**DynamoDB mock assertions**:
- `UpdateCommand` uses `ADD` (not `SET`) for atomic increment
- `ConditionExpression` or initial value handles first-of-day correctly
- TTL attribute is a Unix timestamp (number), not ISO 8601

#### 5.14 Chat Route — Budget Integration & Anthropic SDK

File: `src/api/src/__tests__/routes/chat.test.ts` (extended from PoC)

The PoC chat tests validated stub mode and `parseSuggestions`. MVP adds real SDK mock, budget enforcement, and tool use.

| Test | Why Critical |
|------|-------------|
| Budget exceeded before LLM call → 429 `BUDGET_EXCEEDED` with `reset_at` | No LLM cost incurred when budget is hit |
| Budget exceeded response shape matches API-CONTRACTS.md §5.11 | `{ error: { code, message, details: { scope, reset_at, input_tokens_used, output_tokens_used } } }` |
| Rate limit exceeded → 429 `RATE_LIMITED` with `retry_after` | Per-user 20 messages/hour |
| Successful chat → `incrementUsage()` called with actual token counts | SDK response `usage.input_tokens` and `usage.output_tokens` passed to budget service |
| Tool use: `get_farm_data` tool call → returns farm data for authenticated user only | Tool respects ownership |
| Tool use: `get_weather` tool call → returns weather for user's farm | Tool fetches correct farm coordinates |
| Conversation history: `conversation_id` provided → history loaded from DynamoDB | Multi-turn support |
| Conversation turn limit: >20 messages → 429 | FR-9.10 |
| Anthropic SDK error → 502 `UPSTREAM_ERROR` | Resilience path |

## 7. Auth Testing Strategy

### How to mock Cognito in tests

**Approach**: Generate JWTs locally with `jsonwebtoken` (dev dependency). The Hono auth middleware extracts claims from the `Authorization: Bearer <token>` header. In tests, we control the token content directly.

```typescript
// test-helpers/auth.ts
import jwt from 'jsonwebtoken';

const TEST_PRIVATE_KEY = '...'; // RSA key for test signing only

export function makeTestJwt(claims?: Partial<CognitoClaims>): string {
  return jwt.sign({
    sub: TEST_USER_ID,
    email: 'test@example.com',
    token_use: 'access',
    iss: 'https://cognito-idp.ap-northeast-1.amazonaws.com/test-pool-id',
    client_id: 'test-client-id',
    ...claims,
  }, TEST_PRIVATE_KEY, { algorithm: 'RS256', expiresIn: '1h' });
}

export function makeExpiredJwt(): string {
  return jwt.sign({ sub: TEST_USER_ID, token_use: 'access' },
    TEST_PRIVATE_KEY, { algorithm: 'RS256', expiresIn: '-1h' });
}
```

**Alternative (simpler)**: If the Hono auth middleware uses a verification function that can be mocked, mock the verifier to return decoded claims directly. This avoids the `jsonwebtoken` dependency entirely. Preferred if the middleware is designed for testability.

### Ownership enforcement test pattern

```typescript
// Pattern: User A authenticated, requesting User B's resource
it('returns 404 when user does not own the farm', async () => {
  const userAToken = makeTestJwt({ sub: 'user-A' });
  vi.mocked(dynamoRepo.getFarm).mockResolvedValue({
    ...farmSeed,
    user_id: 'user-B', // Farm belongs to a different user
  });

  const res = await app.request(`/api/v1/farms/${FARM_ID}`, {
    headers: { Authorization: `Bearer ${userAToken}` },
  });

  expect(res.status).toBe(404);  // NOT 403
  const body = await res.json();
  expect(body.error.code).toBe('NOT_FOUND');
});
```

### Auth error response format

Two distinct formats to test:
1. **API Gateway 401** (production only): `{ "message": "Unauthorized" }` — simple format
2. **Hono middleware 401** (testable): `{ "error": { "code": "UNAUTHORIZED", "message": "..." } }` — standard ErrorResponse envelope

Tests exercise path #2 since they call Hono directly (bypassing API Gateway).

## 8. Budget Controls Testing

### Architecture overview (for test design)

```
Chat Route → BudgetService.checkBudget(userId) → DynamoDB GetItem (usage counter)
                                                         ↓
                                                  if allowed: proceed to Anthropic SDK
                                                         ↓
                                                  Anthropic SDK response includes:
                                                    usage: { input_tokens, output_tokens }
                                                         ↓
                                                  BudgetService.incrementUsage(userId, tokens)
                                                         ↓
                                                  DynamoDB UpdateCommand (ADD atomic counter)
```

### How to test token counting without calling Anthropic API

Mock `@anthropic-ai/sdk` to return controlled responses with known token counts:

```typescript
vi.mock('@anthropic-ai/sdk', () => ({
  default: class MockAnthropic {
    messages = {
      create: vi.fn().mockResolvedValue({
        content: [{ type: 'text', text: 'Test response' }],
        usage: { input_tokens: 150, output_tokens: 50 },
        stop_reason: 'end_turn',
      }),
    };
  },
}));
```

Then assert that `incrementUsage()` is called with `{ input_tokens: 150, output_tokens: 50 }`.

## B10-2. Coverage Gaps — Ranked by Risk

### HIGH RISK

**H1. POST diary with harvest fields — not tested at API level**

The diary route test (`diary.test.ts`) creates entries with `category: 'planting'` only. No test creates a `category: 'harvesting'` entry with `harvest_amount`, `harvest_unit`, `revenue`, and `revenue_currency` and verifies these fields appear in the 201 response.

- **Why it matters**: The Zod schema contract test validates the shape, but does not confirm the API route correctly passes harvest fields through `dynamoRepo.createDiaryEntry()` and returns them in the response enrichment step (where `bed_name`, `cost_total`, and `created_by_name` are added).
- **What could break silently**: Harvest fields could be silently stripped by the route handler, or the response builder could omit them. The contract test would still pass because it tests the schema in isolation.

**H2. Harvest refine guard at API level — not tested end-to-end**

The Zod schema correctly rejects `harvest_amount` on a `planting` entry (contract test confirms). But no route-level test sends such a request to verify the API returns 400.

- **Why it matters**: If the route handler does its own body parsing (or uses a different schema path), the refine guard might not fire.
- **What could break silently**: A code change that alters the schema import in `diary.ts` could bypass the refine guard without breaking any existing test.

**H3. PATCH diary with harvest fields — not tested**

No test updates a diary entry to add/change harvest fields. The `UpdateDiaryEntrySchema` has its own refine guard, but it is not tested at the route level.

- **Why it matters**: The update path has different code from create (it reads existing entry, merges, validates). Harvest fields in the update payload could be ignored or could bypass the refine guard.

### MEDIUM RISK

**M1. PATCH farm with `default_currency` — not tested**

The farm PATCH route accepts `default_currency` in the body (confirmed in `farms.ts` line 554), but `farms.test.ts` has no test that patches it. The only test is in the contract suite validating the schema shape.

- **Why it matters**: `default_currency` drives the entire ROI dashboard filtering. If the API silently ignores the PATCH, users cannot switch currencies.

**M2. `UpdateDiaryEntrySchema` harvest refine guard — not contract-tested**

Contract tests validate `CreateDiaryEntrySchema` refine guard (reject harvest on non-harvesting). But `UpdateDiaryEntrySchema` has the same refine and is NOT explicitly contract-tested.

- **Why it matters**: Create and Update schemas could diverge. If someone removes the refine from the update schema, no test catches it.

**M3. Backward compatibility — old entries without harvest fields**

No test confirms that diary entries created before Beta-10 (missing `harvest_amount`, `harvest_unit`, `revenue`, `revenue_currency`) still parse correctly through `DiaryEntryResponseSchema` and render in ROI utils without errors.

- **Why it matters**: DynamoDB items created before Beta-10 will not have these attributes. The schema marks them as `nullable()`, but no test verifies the API response correctly coerces `undefined` (DynamoDB omission) to `null`.

**M4. GET diary list returns harvest fields**

The GET list test checks `data` array length and `meta`, but never inspects whether harvest fields are present on returned entries. A serialization bug could drop them.

### LOW RISK

**L1. ROI floating-point edge cases**

The 32 roi-utils tests use round numbers (500, 1000, 5000). No test checks floating-point precision (e.g., `0.1 + 0.2` style issues). Given that amounts are user-entered and stored as numbers, this is low risk but worth a sanity check.

**L2. DynamoDB service layer — harvest field persistence**

`dynamodb.test.ts` has no diary-related tests at all. The service layer is tested indirectly through route tests that mock DynamoDB. Low risk because:
- The DynamoDB service is a thin wrapper around `PutItem`/`UpdateItem`
- Route tests confirm the mock is called with expected arguments

**L3. UI components — no tests exist**

Five new components (RoiDashboard, RoiSummaryCards, CostByCategoryChart, MonthlyTrendChart, RoiByBedTable) plus DiaryEntryForm harvest section and SetupForm currency setting have zero test coverage. This is expected at MVP scope. The ROI computation logic is covered by `roi-utils.test.ts`; the components are display-only wrappers.
