## 1. Testing Philosophy (PoC)

### Why we test at PoC level

The PoC has six concrete exit criteria (EC-1 through EC-6). Two of them (EC-1 through EC-4) are fully automatable: they involve data flowing through the upload → store → retrieve → display pipeline. Automated tests give us confidence that the pipeline holds together before we spend time on manual deployment verification.

The three highest-risk areas in this codebase — DynamoDB single-table access patterns, multipart image upload validation, and the weather crop-impact transform — all contain pure logic that can be exercised fast and repeatably without standing up AWS resources.

### What we DON'T test at PoC level

- **UI pixel-perfection** — Astro/Preact rendering is verified by manual mobile browser inspection (Checkpoint 4)
- **100% branch coverage** — unnecessary for a feasibility validation
- **Performance benchmarks** — EC-6 (30-second latency) is measured manually post-deploy, not by automated load tests
- **Cost validation** — EC-5 is reviewed in the AWS Billing Console after 24 h of deployment (architecture review, not a test)
- **Real AWS infrastructure** — S3 and DynamoDB are mocked; real behavior is validated by Checkpoint 2 seed data (manual)
- **i18n completeness** — EN/JA string coverage is audited by visual inspection, not automated diff
- **Authentication** — explicitly deferred to MVP (PLANS.md)

## 2. Test Pyramid

```
         /\
        /  \
       / E2E\    ~15%  — Exit criteria manual test script (EXECUTION-PLAN.md §7)
      /------\
     / Integr \  ~55%  — API routes (Hono app.request), middleware chain
    /----------\
   /    Unit    \ ~30%  — Pure functions: validation, key builders, transforms, parsers
  /______________\
```

**Rationale**: This is inverted from a traditional PoC bias toward "just write curl scripts." The reason: the pure-function layer in this codebase is unusually rich — `buildStorageKey`, `wmoToLabel`/`wmoToIcon`, `computeCropImpact`, `parseSuggestions`, `extractIdFromSk`, all 8 validation helpers — and these are the exact spots where silent regressions bite (wrong key format → item not found; wrong WMO mapping → wrong icon). Unit tests here are 2–5 lines each and run in milliseconds. Integration tests use Hono's built-in `app.request()` — no real HTTP server, no real AWS, fast.

**Ratios by line count (estimated)**:
| Layer | Test files | Approx test cases |
|-------|-----------|-------------------|
| Unit (pure functions) | 3 | ~35 |
| Integration (routes + middleware) | 6 | ~55 |
| Service mocks (DynamoDB + S3) | 2 | ~25 |
| **Total** | **11** | **~115** |

## 3. Framework Selection

| Tool | Choice | Reason |
|------|--------|--------|
| **Test runner** | `vitest` | ESM-native, TypeScript-first, no separate babel transform needed; already compatible with the monorepo's `tsconfig.base.json` |
| **Assertion library** | Vitest built-in (`expect`) | No extra dependency |
| **HTTP layer** | `hono/testing` — `app.request()` | Zero-dependency; Hono exports a `fetch`-based test helper that avoids spinning up a real server. Preferable to `supertest` which requires Node's `http.Server`. |
| **AWS SDK mocking** | `aws-sdk-client-mock` | Intercepts `@aws-sdk/*` commands at the client level; supports per-command `.resolves()` and `.rejects()`. Much faster than DynamoDB Local Docker for PoC. |
| **S3 mock** | `aws-sdk-client-mock` | Presigned URL generation is tested via `buildStorageKey` (pure) + mocked `getSignedUrl` return value |
| **External API mocks** | `vi.stubGlobal('fetch', ...)` | Used for Open-Meteo and LLM API calls in weather/chat tests |
| **Frontend testing** | **Skip for PoC** | Type correctness is enforced by `tsc --noEmit`; visual testing is manual (Checkpoint 4 per EXECUTION-PLAN.md) |

**Note on DynamoDB Local**: DynamoDB Local (Docker) would give the most realistic test for GSI queries and `begins_with` key conditions. However, it adds Docker dependency and cold-start time. For PoC, `aws-sdk-client-mock` is sufficient because we're validating the business logic of key construction and result mapping — the actual DynamoDB query behavior was verified during Checkpoint 2 seed data validation. Upgrade to DynamoDB Local at MVP when the table schema becomes more complex.

## 4. Test Architecture

### Where tests live

Co-located with source, under `__tests__/` subdirectories:

```
packages/shared/src/__tests__/
  validation.test.ts
  constants.test.ts

src/api/src/__tests__/
  app.test.ts                          ← middleware chain
  services/
    s3.test.ts
    dynamodb.test.ts
  routes/
    farms.test.ts
    plots.test.ts
    images.test.ts
    weather.test.ts
    chat.test.ts

src/simulator/src/__tests__/
  upload.test.ts
```

Rationale for co-location over a top-level `tests/` directory: each test file's import paths are short (`../validation`, `../../services/dynamodb`), and failures are displayed next to the source they cover in any IDE tree view.

### Fixture strategy

A shared in-memory fixture module (not a separate file — just constants at the top of each test file or a tiny `__tests__/fixtures.ts` per package) provides:

```typescript
// Minimal seed objects matching the real DynamoDB schema
const FARM_ID = 'f0000000-0000-0000-0000-000000000001';
const PLOT_ID = 'a0000000-0000-0000-0000-000000000001';
const IMAGE_ID = 'e0000000-0000-0000-0000-000000000001';

const farmFixture: Farm = {
  id: FARM_ID,
  name: 'Test Farm',
  latitude: 36.0,
  longitude: 138.3,
  locale: 'en',
  theme: 'system',
  created_at: '2026-03-17T00:00:00.000Z',
};
```

Seed data from `scripts/seed-data.ts` is **not** imported into tests — the seed script is for real DynamoDB, tests use in-memory mocks. Fixtures should mirror the seed data IDs so that the E2E test script and unit tests tell the same story.

### Mock boundaries

| Dependency | Strategy | Reason |
|------------|----------|--------|
| **DynamoDB** | `aws-sdk-client-mock` — intercept `GetCommand`, `PutCommand`, `QueryCommand`, `UpdateCommand` | Validates key construction and result mapping without requiring a running table |
| **S3** | `aws-sdk-client-mock` — intercept `PutObjectCommand`, `GetObjectCommand` | Upload tests verify the key format; `getSignedUrl` returns a hardcoded test URL |
| **Open-Meteo API** | `vi.stubGlobal('fetch', mockFetch)` | Returns a static JSON fixture matching the real response shape. Validated once against live API manually. |
| **LLM API (Anthropic/OpenAI)** | `vi.stubGlobal('fetch', mockFetch)` OR no-key stub path | Chat route has a built-in `stubResponse()` when `LLM_API_KEY` is absent — tests can use this path for input/output validation without mocking external API |
| **`crypto.randomUUID()`** | No mock needed | Tests assert on shape/type, not on the specific UUID value |
| **Date/time** | `vi.setSystemTime()` for upload timestamp boundary tests | Used only in the `captured_at` future-date validation test |

## 5. Coverage Plan — By Risk Priority

### Critical (MUST test)

#### 5.1 DynamoDB Repository — 9 Access Patterns + Write Operations

File: `src/api/src/__tests__/services/dynamodb.test.ts`

The single-table design is the highest-risk area. The key construction (`pk.*`, `sk.*` functions) and `extractIdFromSk` parsing are the most fragile parts — a single prefix typo silently produces empty query results.

| Access Pattern | Method | Key Construction Risk | Test |
|---------------|--------|----------------------|------|
| AP-1: Get farm metadata | `getFarm` | `FARM#{farmId}` + `#META` — GetCommand | Assert item mapping: all Farm fields |
| AP-2: Get fields for farm | `getFieldsForFarm` | `begins_with(SK, 'FIELD#')`, `extractIdFromSk` for position-padded SK | Assert position ordering, ID extraction from `FIELD#000001#<uuid>` |
| AP-2b: Get beds for field | `getBedsForField` | `FIELD#{fieldId}`, `begins_with(SK, 'BED#')` | Assert bed ID extraction from padded SK |
| AP-3: Get plots for farm via GSI2 | `getPlotsForFarm` | GSI2 PK = `FARM#{farmId}`, SK extraction from `GSI2SK` | Assert `extractIdFromSk` on `PLOT#<uuid>` format |
| AP-4: Get plot by ID via GSI1 | `getPlotById` | GSI1 PK = `PLOT#{plotId}`, SK = `#META` | Assert `NotFoundError` when no items |
| AP-5: Get images for plot (paginated) | `getImagesForPlot` | `PK = PLOT#{plotId}`, `begins_with(SK, 'IMG#')`, `ScanIndexForward: false` | Assert newest-first ordering, cursor encode/decode roundtrip |
| AP-6: Get image by ID via GSI1 | `getImageById` | GSI1 PK = `IMG#{imageId}` | Assert `NotFoundError` |
| AP-7: Get tags for image | `getTagsForImage` | `PK = IMG#{imageId}`, `begins_with(SK, 'TAG#')` | Assert empty array when no tags |
| AP-8: Write tag | `createTag` | `PutCommand` on `IMG#{imageId}` + `TAG#{createdAt}#{tagId}` | Assert tag object returned; verify PutCommand called |
| AP-9: Update plot status | `createTag` (two-step) | Calls `getPlotById` first (GSI1), then `UpdateCommand` on `BED#{bed_id}` PK | **Critical**: assert UpdateCommand Key uses `bed_id` not `plot_id`; mock both calls |
| Write farm | `createFarm` | `ConditionExpression: attribute_not_exists(PK)` | Assert `ConflictError` on second create attempt |
| Write image | `createImage` | GSI1 projections: `GSI1PK`, `GSI1SK` on image item | Assert both base-table key and GSI key attributes present |

**Pagination boundary**: Test `getImagesForPlot` with a mocked `LastEvaluatedKey` to verify `encodeCursor` produces a non-null `nextCursor`, and that passing that cursor back decodes correctly into `ExclusiveStartKey`.

#### 5.4 Image Upload Route — JPEG Validation (Integration)

The `isJpegBytes` check in `plots.ts:29` validates raw bytes (`0xFF 0xD8 0xFF`), not just the Content-Type header. This is the primary upload security gate.

Tests in `plots.test.ts`:
- A `Uint8Array` starting with `[0xFF, 0xD8, 0xFF]` → accepted
- A PNG header (`[0x89, 0x50, 0x4E, 0x47]`) → 415 UNSUPPORTED_MEDIA_TYPE
- An empty buffer → 415 (0 bytes, no JPEG header)
- A 2MB+1 buffer with valid JPEG header → 413 PAYLOAD_TOO_LARGE

#### 5.5 S3 Service — Storage Key Builder

File: `src/api/src/__tests__/services/s3.test.ts`

`buildStorageKey` is a pure function — no mock needed.

buildStorageKey('farm-001', 'plot-a1', 'img-001', '2026-03-17T10:30:00.000Z')

#### 5.6 Weather Route — Transform + Crop Impact

File: `src/api/src/__tests__/routes/weather.test.ts`

The weather route contains substantial pure logic: WMO code mapping, `transformWeather`, and `computeCropImpact`. These are currently private to the route module — they may need to be extracted or the route tested end-to-end via `app.request()`.

| Test | Why Important |
|------|---------------|
| WMO code 0 → `'Clear sky'` / `'sunny'` | Boundary: most common case |
| WMO code 95 → `'Thunderstorm'` / `'thunderstorm'` | Boundary: highest code with distinct label |
| WMO code 99 → `'Thunderstorm with hail'` | Boundary: catch-all case |
| `computeCropImpact`: frost risk when `temperature_min_c < 2` for frost-sensitive crop | Critical path |
| `computeCropImpact`: only first matching frost day reported (`break`) | Edge: `break` early-exit behavior |
| `computeCropImpact`: non-frost-sensitive crop (lettuce) not in frost impact | Edge: crop tolerance lookup |
| Cache hit: second request within TTL returns cached data without fetch | Critical path (15-min TTL) |
| Cache miss: stale cache served when Open-Meteo fetch fails | Resilience path |

#### 5.7 Chat Route — Validation + Stub Mode

File: `src/api/src/__tests__/routes/chat.test.ts`

The `parseSuggestions` function and `buildSystemPrompt` contain logic worth testing independently.

| Test | Why |
|------|-----|
| `parseSuggestions`: response with `SUGGESTIONS: [...]` line → extracts reply and array | Happy path |
| `parseSuggestions`: no SUGGESTIONS line → full text as reply, default suggestions | Fallback |
| `parseSuggestions`: malformed JSON after SUGGESTIONS: → default suggestions | Resilience |

#### 5.8 Farm Hierarchy — Nested Query Correctness

In `GET /api/v1/farms/:farmId`, the route assembles `fields → beds → plots` via sequential DynamoDB calls. A wrong `bed_id` → `PLOT#` query could silently return empty plots. Test in `farms.test.ts`:

- Mock a farm with 2 fields, 2 beds per field, 2 plots per bed → assert response structure has correct nesting
- A bed with no plots → `plots: []` (not missing key)

## 8. Regression Risk Map

Ranked by likelihood of silent breakage when code changes:

| Area | Risk | Trigger | Detection |
|------|------|---------|-----------|
| **DynamoDB PK/SK format** | HIGH | Any rename of entity prefix strings or padding logic in `sk.*` builders | `dynamodb.test.ts` AP-2, AP-5 tests |
| **`extractIdFromSk` parsing** | HIGH | Change to SK format (e.g. add extra `#` separator) silently returns wrong IDs | `dynamodb.test.ts` AP-2, AP-2b, AP-3 tests |
| **`createTag` two-step update** | HIGH | `UpdateCommand` targets `BED#{bed_id}` not `PLOT#{plot_id}` — wrong key → silent no-op | `dynamodb.test.ts` AP-9 test asserting `Key.PK` |
| **Image upload field names** | HIGH | `trigger_type` vs `trigger` mismatch (confirmed bug, see §5.10) | `plots.test.ts` upload happy path + `upload.test.ts` |
| **API response shapes** | MEDIUM | Adding/removing fields from route handlers drifts from `@litcrop/shared` API types | TypeScript (`tsc --noEmit`) + `farms.test.ts` response shape assertions |
| **JPEG magic byte check** | MEDIUM | Change to `isJpegBytes` byte offset (`buf[0]`, `buf[1]`, `buf[2]`) | `plots.test.ts` non-JPEG rejection test |
| **Weather cache key** | MEDIUM | Cache keyed by `farmId` — if farm ID format changes, cache key may diverge | `weather.test.ts` cache hit test |
| **`computeCropImpact` early break** | LOW | The `break` in frost/heat/rain loops means only the nearest event is reported — easy to accidentally remove | `weather.test.ts` multi-day frost scenario |
| **Cursor encode/decode** | LOW | `base64url` encoding of `ExclusiveStartKey` — DynamoDB key structure change breaks cursor | `dynamodb.test.ts` pagination cursor roundtrip |

## 9. Non-Functional Testing (PoC scope)

### Security

Validate the following OWASP-relevant items via API route tests (already planned above):

| Risk | Mitigation | Test Coverage |
|------|-----------|---------------|
| **Unrestricted file upload** | JPEG magic-byte check + 2MB limit | `plots.test.ts` §5.4 |

| **Invalid enum injection** | `isValidTagValue`, `isValidTriggerType` guard all enum fields | `validation.test.ts`, `plots.test.ts`, `images.test.ts` |

| **Oversized text input** | Note (500 chars), description (500 chars), message (2000 chars) | `images.test.ts`, `chat.test.ts` |

**Not tested at PoC**: SQL/NoSQL injection (DynamoDB parameterized expressions prevent this by design), authentication/authorization (deferred to MVP), CORS enforcement (requires real browser cross-origin test).

Skip for PoC. Lambda auto-scales; the PoC has a single user. EC-6 (< 30s e2e) is measured manually post-deploy per EXECUTION-PLAN.md §7.

### Accessibility

Skip for PoC. Manual check at Checkpoint 4 using Chrome DevTools accessibility panel (per EXECUTION-PLAN.md §3.4).
