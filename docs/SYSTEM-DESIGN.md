## 1. Sequence Diagrams

> **MVP Auth Note**: All `/api/v1/*` endpoints (except `/health`) are protected by an API Gateway JWT Authorizer backed by Cognito User Pools ([ADR-007](decisions/ADR-20260320-authentication-provider.md)). JWT validation happens at the gateway level (~1ms, zero Lambda cost). The sequence diagrams below show the Hono middleware extracting user identity from the already-validated JWT claims.

### 1.0a User Registration Flow (MVP)

```mermaid
sequenceDiagram
    participant B as Browser
    participant CUI as Cognito Hosted UI
    participant CUP as Cognito User Pool
    participant SES as Email (Cognito Default)

    B->>CUI: Navigate to /login (redirect)
    CUI-->>B: Show registration form

    B->>CUI: Submit { email, password }
    CUI->>CUP: SignUp(email, password)
    CUP->>CUP: Validate password policy (8+ chars, mixed case + number)
    CUP->>SES: Send verification email (6-digit code)
    CUP-->>CUI: User created (unconfirmed)
    CUI-->>B: Show verification code input

    B->>CUI: Submit verification code
    CUI->>CUP: ConfirmSignUp(email, code)
    CUP-->>CUI: User confirmed
    CUI-->>B: Redirect to app with auth code

    B->>CUP: Exchange auth code for tokens
    CUP-->>B: { access_token (JWT), refresh_token, id_token }

    Note over B: Store access_token in memory (Preact state)<br/>Store refresh_token in localStorage
```

> **Production hardening**: Storing refresh tokens in `localStorage` is acceptable for MVP (1-10 trusted users, no sensitive financial data), but is vulnerable to XSS. At Production scope, evaluate HttpOnly cookie-based token storage with a BFF (Backend For Frontend) pattern, or Cognito's built-in cookie-based session management.

```mermaid
        SVC-->>RH: Farm + Fields + Beds (nested)
        RH-->>MW: 200 OK { data: { id, name, fields: [...] } }
```

### 1.7 POST /api/v1/plots/{plotId}/images -- Image Upload

```mermaid
sequenceDiagram
    participant CN as Camera Node
    participant AG as API Gateway
    participant L as Lambda/Hono
    participant MW as Middleware Chain
    participant RH as uploadImage Handler
    participant SVC as ImageService
    participant S3 as S3
    participant DB as DynamoDB

    CN->>AG: POST /api/v1/plots/{plotId}/images<br/>Content-Type: multipart/form-data<br/>(image, captured_at, node_id, trigger, metadata?)
    AG->>L: Proxy request (payload limit: 10MB at API GW)
    L->>MW: cors() → logger() → authMiddleware (extract user_id from JWT)
    MW->>RH: Route matched

    RH->>RH: Parse multipart form data
    RH->>RH: Validate: JPEG content-type, size <= 2MB,<br/>captured_at (ISO 8601), trigger (scheduled|motion),<br/>node_id (non-empty), metadata (valid JSON if present)

    alt Validation fails
        RH-->>MW: 400 VALIDATION_ERROR or 415 UNSUPPORTED_MEDIA_TYPE
    else Size exceeds 2MB
        RH-->>MW: 413 PAYLOAD_TOO_LARGE
    else Valid
        RH->>SVC: uploadImage(plotId, imageFile, metadata)

        SVC->>DB: Query GSI1 PK=PLOT#{plotId} SK=#META (verify plot exists)
        alt Plot not found
            SVC-->>RH: PlotNotFoundError
            RH-->>MW: 404 NOT_FOUND
        else Plot exists
            SVC->>SVC: Generate imageId (UUID),<br/>build storage_key: images/{farmId}/{plotId}/{YYYY}/{MM}/{DD}/{imageId}.jpg
            SVC->>S3: PutObject(storage_key, imageBuffer, image/jpeg)
            alt S3 failure
                S3-->>SVC: Error
                SVC-->>RH: StorageError
                RH-->>MW: 503 SERVICE_UNAVAILABLE
            else S3 success
                S3-->>SVC: OK
                SVC->>DB: PutItem PK=PLOT#{plotId} SK=IMG#{capturedAt}#{imageId}
                DB-->>SVC: OK
                SVC->>S3: getSignedUrl(storage_key, 15min)
                S3-->>SVC: Signed URL
                SVC-->>RH: Image record with URL
                RH-->>MW: 201 Created { data: { id, url, captured_at, ... } }
            end
        end
    end

    MW->>L: errorHandler passthrough
    L-->>AG: Response
    AG-->>CN: JSON response
```

### 1.11 POST /api/v1/chat -- AI Chatbot (MVP: Multi-Turn + Tool Use)

```mermaid
sequenceDiagram
    participant B as Browser
    participant AG as API Gateway
    participant L as Lambda/Hono
    participant MW as Middleware Chain
    participant RH as chatMessage Handler
    participant SVC as ChatService
    participant DB as DynamoDB
    participant SDK as Anthropic SDK
    participant OM as Open-Meteo API

    B->>AG: POST /api/v1/chat { message, farm_id?, conversation_id? }
    AG->>AG: JWT Authorizer validates token
    AG->>L: Proxy request (with JWT claims)
    L->>MW: cors() → logger() → authMiddleware (extract user_id from JWT)
    MW->>RH: Route matched

    RH->>RH: Validate body: message non-empty, max 2000 chars

    alt Validation fails
        RH-->>MW: 400 VALIDATION_ERROR
    else Valid
        Note over RH,DB: Budget check (before calling LLM)
        RH->>DB: GetItem PK=USAGE#{userId} SK=DAY#{yyyy-mm-dd}
        DB-->>RH: { input_tokens_used, output_tokens_used } or null
        RH->>DB: GetItem PK=USAGE#GLOBAL SK=DAY#{yyyy-mm-dd}
        DB-->>RH: { input_tokens_used, output_tokens_used } or null

        alt User or global budget exceeded
            RH-->>MW: 429 BUDGET_EXCEEDED { reset_at, scope }
        else Budget available
        RH->>SVC: chat(userId, message, farmId, conversationId)

        Note over SVC,DB: Load conversation history (multi-turn)
        opt conversationId provided
            SVC->>DB: Query PK=CONV#{conversationId} SK begins_with MSG#
            DB-->>SVC: Previous messages[] (up to last N)
        end

        opt farmId provided
            SVC->>DB: Query PK=FARM#{farmId} SK=#META (verify user_id ownership)
            DB-->>SVC: Farm record (lat, lon, climate_zone)
            SVC->>DB: Query GSI2 PK=FARM#{farmId} (all plots)
            DB-->>SVC: Plot records (crops, statuses)
        end

        SVC->>SVC: Build system prompt with farm context

        SVC->>SDK: client.messages.create({<br/>  model: 'claude-haiku-4-5-20251001',<br/>  system: contextPrompt,<br/>  messages: [...history, { role: 'user', content: message }],<br/>  tools: [get_farm_data, get_weather]<br/>})
        SDK-->>SVC: Response (may include tool_use blocks)

        loop Tool use loop (max 5 iterations)
            alt Response contains tool_use
                SVC->>SVC: Dispatch tool call
                opt get_farm_data tool
                    SVC->>DB: Query farm/plot data
                    DB-->>SVC: Result
                end
                opt get_weather tool
                    SVC->>OM: GET open-meteo.com/v1/forecast
                    OM-->>SVC: Weather data
                end
                SVC->>SDK: Send tool_result back
                SDK-->>SVC: Continue response
            else Response is text (no tool_use)
                Note over SVC: Exit loop
            end
        end

        Note over SVC,DB: Save conversation history
        SVC->>DB: PutItem PK=CONV#{convId} SK=MSG#{ts}#user<br/>(+ assistant response, TTL: 24h)

        Note over SVC,DB: Update usage counters (after LLM response)
        SVC->>DB: UpdateItem PK=USAGE#{userId} SK=DAY#{date}<br/>ADD input_tokens_used +N, output_tokens_used +M (TTL: 48h)
        SVC->>DB: UpdateItem PK=USAGE#GLOBAL SK=DAY#{date}<br/>ADD input_tokens_used +N, output_tokens_used +M (TTL: 48h)

        SVC-->>RH: { reply, suggestions[], conversation_id }
        end
        RH-->>MW: 200 OK { data: { reply, suggestions, conversation_id } }
    end

    MW->>L: errorHandler passthrough
    L-->>AG: Response
    AG-->>B: JSON response
```

### 1.12 Image Processing Pipeline — Thumbnail Generation (MVP)

```mermaid
sequenceDiagram
    participant CN as Camera Node
    participant AG as API Gateway
    participant L as Lambda/Hono
    participant S3 as S3 (images bucket)
    participant S3E as S3 Event Notification
    participant TL as Thumbnail Lambda
    participant DB as DynamoDB

    CN->>AG: POST /api/v1/plots/{plotId}/images (JPEG upload)
    AG->>L: Proxy request
    L->>S3: PutObject images/{farmId}/{plotId}/{date}/{imageId}.jpg
    S3-->>L: OK
    L->>DB: PutItem (Image record with storage_key)
    L-->>CN: 201 Created

    Note over S3,TL: Async — S3 event triggers thumbnail Lambda
    S3->>S3E: s3:ObjectCreated event (prefix: images/)
    S3E->>TL: Invoke with event { bucket, key }

    TL->>S3: GetObject (original JPEG)
    S3-->>TL: Image buffer

    TL->>TL: Resize to 300x300 (sharp or jimp)<br/>Maintain aspect ratio, crop center

    TL->>S3: PutObject thumbnails/{farmId}/{plotId}/{date}/{imageId}.jpg
    S3-->>TL: OK

    TL->>DB: UpdateItem Image: SET thumbnail_key = thumbnails/...
    DB-->>TL: OK

    Note over TL: Thumbnail available within ~2-5 seconds of upload
```

**Key design decisions**:
- **Async processing**: Thumbnail generation does not block the upload response — the camera node gets `201` immediately
- **Separate Lambda**: Isolates image processing from the API Lambda (different memory/timeout requirements)
- **S3 event trigger**: No polling or queue needed — S3 natively invokes Lambda on object creation
- **Thumbnail size**: 300x300px center-crop covers both mobile grid tiles and desktop list views
- **CDK construct**: S3 bucket notification → Lambda trigger defined in `LitCropStack`

## 4. Error Handling Strategy

### 4.1 Error Classification

All errors in the system are classified into a hierarchy that determines how they propagate and are displayed.

```
API Gateway (pre-Lambda):
├── 401 Unauthorized    → JWT missing, expired, or invalid (Cognito JWT Authorizer)

AppError (base) — within Lambda/Hono:
├── ValidationError     → 400 VALIDATION_ERROR
├── ContentTypeError    → 415 UNSUPPORTED_MEDIA_TYPE
├── NotFoundError       → 404 NOT_FOUND (also used when user_id doesn't match — prevents info leak)
├── PayloadTooLargeError → 413 PAYLOAD_TOO_LARGE
├── StorageError        → 503 SERVICE_UNAVAILABLE
├── ExternalApiError    → 502 (weather, LLM failures)
└── (unclassified)      → 500 INTERNAL_ERROR
```

> **MVP note**: `401 Unauthorized` is handled at the API Gateway level by the JWT Authorizer — it never reaches the Lambda function. If a request has a valid JWT but the user doesn't own the requested resource, the API returns `404 NOT_FOUND` (not `403 Forbidden`) to avoid leaking resource existence.

### 4.2 Error Propagation: Service → Middleware → Client

```typescript
// src/api/src/middleware/error-handler.ts

import { Context, Next } from 'hono';
import { AppError } from '../errors';

/**
 * Global error handler middleware.
 * Services throw typed AppError subclasses.
 * Routes do NOT catch errors — they propagate up to this middleware.
 * This ensures a consistent error response format across all endpoints.
 */
export async function errorHandler(c: Context, next: Next) {
  try {
    await next();
  } catch (err) {
    if (err instanceof AppError) {
      // Known error — map to structured response
      return c.json(
        {
          error: {
            code: err.code,
            message: err.message,
            details: err.details ?? {},
          },
        },
        err.statusCode
      );
    }

    // Unknown error — log and return generic 500
    console.error('Unhandled error:', err);
    return c.json(
      {
        error: {
          code: 'INTERNAL_ERROR',
          message: 'An unexpected error occurred.',
          details: {},
        },
      },
      500
    );
  }
}
```

### 4.3 Service-Level Error Throwing

```typescript
// src/api/src/errors.ts

export class AppError extends Error {
  constructor(
    public readonly code: string,
    message: string,
    public readonly statusCode: number,
    public readonly details?: Record<string, unknown>
  ) {
    super(message);
  }
}

export class NotFoundError extends AppError {
  constructor(resource: string, id: string) {
    super('NOT_FOUND', `${resource} '${id}' not found`, 404);
  }
}

export class ValidationError extends AppError {
  constructor(message: string, details?: Record<string, unknown>) {
    super('VALIDATION_ERROR', message, 400, details);
  }
}

export class PayloadTooLargeError extends AppError {
  constructor(maxBytes: number) {
    super('PAYLOAD_TOO_LARGE', `Payload exceeds ${maxBytes} bytes`, 413);
  }
}

export class StorageError extends AppError {
  constructor(message: string) {
    super('SERVICE_UNAVAILABLE', message, 503);
  }
}
```

### 4.4 Route Handler Pattern

Route handlers validate inputs and call services. They do **not** catch errors — errors propagate to `errorHandler` middleware.

```typescript
// Example: src/api/src/routes/tags.ts

import { Hono } from 'hono';
import type { ITagService } from '../services/types';

export function tagRoutes(tagService: ITagService) {
  const app = new Hono();

  app.post('/api/v1/images/:imageId/tags', async (c) => {
    const { imageId } = c.req.param();
    const body = await c.req.json();

    // Validation (throws ValidationError on failure)
    validateTagInput(body);

    // Service call (throws NotFoundError if image missing)
    const result = await tagService.addTag(imageId, body);

    return c.json({ data: result }, 201);
  });

  return app;
}
```

### 4.5 Frontend Error Handling

| Error Source | Detection | User Feedback | Recovery |
|-------------|-----------|---------------|----------|
| API 401 (unauthorized) | Response status check | Redirect to /login | Auto-refresh token; if refresh fails, full re-login |
| API 400 (validation) | Response status check | Toast with error message | Fix input and retry |
| API 404 | Response status check | Navigate to "not found" state | Back navigation |
| API 413 | Response status check | Camera node logs warning | Reduce image quality |
| API 500 | Response status check | Full-page or inline error state | Retry button |
| API 503 | Response status check | "Service temporarily unavailable" | Auto-retry after delay |
| Network offline | `navigator.onLine` + fetch catch | Yellow banner: "You are offline" | Auto-retry on reconnect |
| S3 signed URL expired (403) | Image `onerror` event | Silent re-fetch of parent resource | Transparent to user |
| Tag save failure | POST catch | Revert optimistic UI + error toast | "Tap to retry" on toast |

### 4.6 Camera Simulator Error Handling

```
Upload attempt
  ├── Success (201) → log, wait for next interval
  ├── 400/413 → log error, skip this image (do not retry)
  ├── 404 → log error, halt (configuration issue)
  ├── 500/503/network error → retry with exponential backoff
  │     ├── Attempt 1: wait 1s
  │     ├── Attempt 2: wait 2s
  │     ├── Attempt 3: wait 4s
  │     ├── Attempt 4: wait 8s
  │     └── Attempt 5: wait 16s → give up, log failure, continue to next
  └── Timeout (30s) → treat as network error → retry
```

## 5. Caching Strategy

### 5.1 Caching Layers Overview

```
Layer 1: CloudFront (static assets)           TTL: long-lived
Layer 2: Lambda in-memory (weather proxy)     TTL: 15 minutes
Layer 3: S3 signed URLs (image access)        TTL: 15 minutes
Layer 4: Browser cache (assets + API)         TTL: varies
```

### 5.2 Weather Proxy Cache

| Aspect | Strategy |
|--------|----------|
| **Store** | Lambda in-memory (module-level `Map`) |
| **Key** | `weather:{farmId}` |
| **TTL** | 15 minutes |
| **Invalidation** | Time-based only; no manual invalidation in PoC |
| **Cold start** | Lambda cold start clears cache; first request after cold start calls Open-Meteo |
| **Fallback** | If Open-Meteo is unreachable, return stale cache (if exists) with `stale: true` flag |

```typescript
// Conceptual implementation
const cache = new Map<string, { data: WeatherResponse; timestamp: number }>();
const WEATHER_TTL_MS = 15 * 60 * 1000; // 15 minutes

function getCachedWeather(farmId: string): WeatherResponse | null {
  const entry = cache.get(`weather:${farmId}`);
  if (entry && Date.now() - entry.timestamp < WEATHER_TTL_MS) {
    return entry.data;
  }
  return null;
}
```

**Why in-memory for MVP?** At 1-5 users with 1 farm each, a Lambda module-level `Map` keyed by `farmId` is sufficient. The cache is per-Lambda-instance, so concurrent users may trigger redundant Open-Meteo calls during cold starts — acceptable at MVP scale. At Production scale (many farms, concurrent users), migrate to DynamoDB TTL-based caching to survive cold starts and reduce external API calls.

### 5.3 S3 Signed URL Expiry

| Aspect | Strategy |
|--------|----------|
| **Expiry** | 15 minutes |
| **Generated by** | `@aws-sdk/s3-request-presigner` in Lambda |
| **Used for** | All image access (thumbnails and full-size) |
| **Frontend handling** | If image load fails with 403, re-fetch parent API endpoint for fresh URLs |
| **Per-request** | Each API response generates fresh signed URLs (not cached) |

**Why 15 minutes?** Balances security (short-lived access) with usability (user check-in sessions are 1-3 minutes, leaving margin for slow connections and browsing).

### 5.4 Static Asset Caching (CloudFront + S3)

| Asset Type | Cache-Control Header | CloudFront TTL | Notes |
|-----------|---------------------|----------------|-------|
| HTML pages | `no-cache, must-revalidate` | 0 (always origin) | Ensures latest content |
| CSS/JS (hashed) | `public, max-age=31536000, immutable` | 1 year | Astro adds content hashes to filenames |
| Fonts | `public, max-age=31536000` | 1 year | System fonts, rarely changes |
| favicon/icons | `public, max-age=86400` | 24 hours | |

### 5.5 Browser-Level Caching

| Resource | Cache Strategy |
|----------|---------------|
| Astro static HTML | `ETag` + `If-None-Match` (304 responses) |
| Hashed JS/CSS bundles | Immutable cache (filename changes on content change) |
| API responses (`/api/*`) | `Cache-Control: no-store` (always fetch fresh) |
| S3 signed URL images | Not browser-cached (URL changes each request due to signature) |

## 6. Frontend Architecture

### 6.1 Rendering Strategy: Astro SSG + Preact Islands

The frontend uses Astro's **Static Site Generation (SSG)** for the page shell and **Preact Islands** for interactive components. This delivers near-zero JavaScript for the static layout while hydrating only the components that need interactivity.

```
  Astro Build (SSG)                 Browser (Runtime)
  ─────────────────                 ──────────────────
  ┌─────────────────┐              ┌─────────────────┐
  │  BaseLayout     │ ──── HTML ──>│  Static shell    │  0 KB JS
  │  NavigationHeader│             │  Header, footer  │
  │  Page structure  │             │  CSS tokens       │
  └─────────────────┘              └─────────────────┘
                                           │
  ┌─────────────────┐              ┌───────▼─────────┐
  │  Preact Islands  │ ─── JS ───>│  Hydrated islands│  ~15-30 KB JS
  │  (client:load)   │            │  API fetch + UI  │
  │  (client:visible)│            │  Event handlers  │
  └─────────────────┘              └─────────────────┘
```

### 6.2 Island Hydration Directives

| Island Component | Directive | Rationale |
|-----------------|-----------|-----------|
| `PlotList` | `client:load` | Core content, must render immediately with API data |

| `ThemeSwitcher` | `client:load` | Must respond to user preference immediately |
| `ToastContainer` | `client:load` | Global notification layer, must be ready for any action |

### 6.3 Page Routing (Astro MPA)

Astro generates static HTML files for each page. Navigation is standard browser navigation (full page loads), not client-side SPA routing. This provides:

- **Simpler mental model**: each page is a separate HTML file
- **Better performance on slow connections**: HTML loads before JS
- **Browser-native back/forward**: history management is free

```
src/frontend/src/pages/
  login.astro                     →  /login               (MVP: Cognito login redirect)
  callback.astro                  →  /callback            (MVP: OAuth callback handler)
  index.astro                     →  /                    (Farm Overview) [protected]
  layout.astro                    →  /layout              (Farm Layout View) [protected]
  plot/[plotId].astro             →  /plot/{plotId}        (Plot Detail) [protected]
  plot/[plotId]/images.astro      →  /plot/{plotId}/images (Image Timeline) [protected]
  weather.astro                   →  /weather             (Weather & Environment) [protected]
  setup.astro                     →  /setup               (Farm Setup & AI) [protected]
  settings.astro                  →  /settings            (Settings) [protected]
```

**MVP auth routing**: Pages marked `[protected]` check for a valid session on load. If no session exists, the user is redirected to `/login`, which redirects to the Cognito Hosted UI. After login, Cognito redirects back to `/callback`, which exchanges the auth code for tokens and redirects to `/`.

**Navigation flow**: Users navigate via `<a href="...">` links. Preact islands handle in-page interactions (tagging, image browsing, chat). No client-side router is needed.

### 6.5 Key Frontend Patterns

**API fetch on mount**: Each Preact island fetches its own data on mount. The farm ID is passed as a prop from the Astro page (read from config or URL).

```typescript
// Example: PlotList island
import { useEffect, useState } from 'preact/hooks';
import { apiClient } from '../lib/api-client';

export function PlotList({ farmId }: { farmId: string }) {
  const [plots, setPlots] = useState<FarmPlotItem[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    apiClient.getFarmPlots(farmId)
      .then(res => setPlots(res.data))
      .catch(err => setError(err.message))
      .finally(() => setLoading(false));
  }, [farmId]);

  if (loading) return <PlotListSkeleton />;
  if (error) return <ErrorState message={error} onRetry={() => { /* refetch */ }} />;
  return <>{plots.map(plot => <PlotTile key={plot.id} plot={plot} />)}</>;
}
```

**Optimistic UI for tagging**: Tag buttons apply the visual state immediately, then fire the API call. If the call fails, the UI reverts and shows an error toast.

**Cross-island communication**: Minimal. When a tag is applied in `TagButtons`, it emits a browser `CustomEvent` that `ToastContainer` listens for. No shared state store is needed — each island is self-contained.

```typescript
// TagButtons emits:
window.dispatchEvent(new CustomEvent('litcrop:toast', {
  detail: { type: 'success', message: 'Healthy tag applied' }
}));

// ToastContainer listens:
useEffect(() => {
  const handler = (e: CustomEvent) => showToast(e.detail);
  window.addEventListener('litcrop:toast', handler);
  return () => window.removeEventListener('litcrop:toast', handler);
}, []);
```

```typescript
// src/frontend/src/i18n/index.ts

import en from './en.json';
import ja from './ja.json';
import type { Locale } from '@litcrop/shared';

const translations: Record<Locale, Record<string, string>> = { en, ja };

let currentLocale: Locale = 'en';

export function setLocale(locale: Locale) {
  currentLocale = locale;
  document.documentElement.lang = locale;
}

export function getLocale(): Locale {
  return currentLocale;
}

/**
 * Translate a key with optional interpolation.
 * Usage: t('plot.detail', { label: 'A1', crop: 'Tomato' })
 *        → "Plot A1: Tomato" (en)
 *        → "区画A1：Tomato" (ja)
 */
export function t(key: string, params?: Record<string, string | number>): string {
  let text = translations[currentLocale]?.[key] ?? translations.en[key] ?? key;
  if (params) {
    for (const [k, v] of Object.entries(params)) {
      text = text.replace(`{${k}}`, String(v));
    }
  }
  return text;
}
```

```typescript
import type { Theme, Locale, TempUnit } from '@litcrop/shared';

const PREFS_KEY = 'litcrop-prefs';

interface UserPreferences {
  theme: Theme;
  locale: Locale;
  tempUnit: TempUnit;
}

/** Apply theme to document — called on page load and on change */
export function applyTheme(theme: Theme) {
  document.documentElement.setAttribute('data-theme', theme);
  savePreference('theme', theme);
}

/** Read preferences from localStorage */
export function getPreferences(): UserPreferences {
  const stored = localStorage.getItem(PREFS_KEY);
  return stored
    ? JSON.parse(stored)
    : { theme: 'system', locale: 'en', tempUnit: 'C' };
}

function savePreference<K extends keyof UserPreferences>(
  key: K, value: UserPreferences[K]
) {
  const prefs = getPreferences();
  prefs[key] = value;
  localStorage.setItem(PREFS_KEY, JSON.stringify(prefs));
}
```

## 8. State Management

### 8.1 State Management Philosophy

LitCrop has **no global state store**. Each Preact island manages its own local state via `useState`/`useReducer`. This is deliberate:

- **Astro MPA**: Pages are separate HTML files — no shared memory between pages
- **Island isolation**: Each island fetches its own data and manages its own lifecycle
- **MVP scale**: 6 plots, 1-5 users — no complex state synchronization needed

**MVP addition**: Auth state (access token, user info) is the one piece of state that spans all pages. It's managed by the auth client module (Section 2.7) and stored in memory + `localStorage`, not in a state library.

### 8.2 Data Flow Pattern

### 8.4 Cross-Page State Persistence

| State | Persistence | Mechanism |
|-------|-------------|-----------|
| Auth tokens (MVP) | Memory + `localStorage` | Access token in Preact context; refresh token in `localStorage` |
| User identity (MVP) | Derived from JWT | `sub` (userId) and `email` decoded from access token claims |
| User locale | `localStorage` + Farm API | `litcrop-prefs.locale` → used on page load; synced to API on change |
| User theme | `localStorage` + Farm API | `litcrop-prefs.theme` → applied before paint; synced to API on change |
| Temp unit | `localStorage` + Farm API | `litcrop-prefs.tempUnit` |
| Farm ID | Derived from user's farms | MVP: query user's farms on login; single-farm per user |
| Conversation ID (MVP) | Session memory | ChatWidget maintains `conversationId` for multi-turn; lost on page navigation |
| Scroll position | Browser native | Astro MPA — browser manages `history.scrollRestoration` |

### 8.5 Stale Data Handling

Since the app uses Astro MPA (full page loads), stale data is naturally resolved:

- **Navigating back to Farm Overview** after tagging: triggers a fresh `GET /farms/{id}/plots` fetch, which returns the updated `latest_status`
- **Signed URL expiry**: If an `<img>` fails to load (S3 returns 403), the island catches the `onerror` event and re-fetches the parent API endpoint for fresh URLs
- **Weather cache**: The 15-minute server-side cache means weather data may be up to 15 minutes stale — acceptable for farming use case

### 8.6 No State Library Justification

| Factor | Assessment |
|--------|-----------|
| Shared state across islands? | Minimal — toast events + auth token cross boundaries |
| Complex state transitions? | No — simple loading/data/error pattern |
| Server state synchronization? | Handled by re-fetching on page mount |
| Number of state consumers? | 1-2 per data source (island-local) |
| MVP scope? | 6 plots, 1 farm, 1-5 users |

A state library (Redux, Zustand, Jotai) would add bundle size and complexity without solving a real problem at MVP scale. Auth state is managed by the auth client module (not a state library). If Production introduces cross-island shared state (e.g., real-time updates via WebSocket), evaluate `@preact/signals` for lightweight reactivity.

#### State Shape

```typescript
interface TimeLapseState {
  status: 'idle' | 'loading' | 'ready' | 'playing' | 'paused' | 'error';
  allImages: ImageListItem[];     // All images for this plot (all pages)
  weeks: WeekGroup[];             // Images grouped by ISO week
  selectedWeekIndex: number;      // Currently selected week
  frames: TimeLapseFrame[];       // Frames for selected week, oldest-first
  currentIndex: number;
  speed: 0.5 | 1 | 2;            // Multiplier (1x=30fps default)
  loadProgress: { loaded: number; total: number };
  error: string | null;
}

interface WeekGroup {
  weekStart: string;              // ISO date (Monday)
  weekEnd: string;                // ISO date (Sunday)
  images: ImageListItem[];        // Images in this week, oldest-first
  complete: boolean;              // true if 7 days of data exist
}

interface TimeLapseFrame {
  id: string;
  thumbnailUrl: string;           // 300x300 thumbnail for playback
  capturedAt: string;             // ISO 8601
  trigger: TriggerType;
  preloaded: boolean;             // true after Image() onload fires
}
```

#### Data Loading Strategy

```
1. On component mount (not on play tap):
   - Fetch all pages of GET /plots/{plotId}/images
   - Accumulate all ImageListItem[]
   - Group by ISO week (Mon-Sun), sort each group oldest-first
   - Mark complete weeks (7 unique days)
   - Show week selector with available weeks

2. User selects a week (preloading starts immediately):
   - Map selected week's images to TimeLapseFrame[]
   - Batch-preload all thumbnails (6 parallel via new Image().src)
   - Play button enables after 50 frames preloaded

3. User taps "Play This Week":
   - Start playback at 30fps (1x) after 50+ frames ready
   - Continue preloading remaining frames in background
```

**Why thumbnails**: 300x300 JPEGs are ~15-30KB each. A full week (~294 frames) = ~5.7MB. Full-size images would be ~441MB — impossible on LTE in the field.

**Week grouping**: Uses `getISOWeek()` from captured_at timestamp. Camera schedule produces ~42 images/day. Complete weeks have all 7 days represented. Current (incomplete) week shows progress but is not playable.

#### Animation Loop

```typescript
// Speed mapping:
//   0.5x → 15fps (show every frame, 33ms interval)
//   1x   → 30fps (show every frame, 33ms interval) — DEFAULT
//   2x   → 30fps (skip every 2nd frame, 33ms interval)
const BASE_FPS = 30;
const frameInterval = state.speed >= 1 ? 1000 / BASE_FPS : 1000 / 15;
const frameStep = state.speed === 2 ? 2 : 1;
let lastFrameTime = 0;

function animate(timestamp: number) {
  if (state.status !== 'playing') return;
  if (timestamp - lastFrameTime >= frameInterval) {
    lastFrameTime = timestamp;
    setCurrentIndex(prev => {
      let next = prev + frameStep;
      if (next >= frames.length) next = 0;  // Loop
      // If next frame not preloaded, pause with buffering indicator
      if (!frames[next].preloaded) {
        setStatus('buffering');
        return prev;
      }
      return next;
    });
  }
  rafId = requestAnimationFrame(animate);
}
```

**Preload strategy**: Preloading starts on week selection (not play tap). 6 parallel `new Image()` requests. Play button enables after 50 frames. At 30fps, 50 frames = 1.7s of headroom — typically enough for the remaining ~244 frames to finish loading (~4.8MB at ~5Mbps LTE = ~8s, well within the 10s playback window).

**`prefers-reduced-motion`**: If true, auto-play disabled; manual stepping only.

#### Time-Proportional Progress Bar

The progress bar maps frame position to real clock time, not frame index. This means morning/afternoon dense capture windows (15-min intervals) compress visually, while midday sparse windows (30-min intervals) expand.

```typescript
function getProgressPercent(frame: TimeLapseFrame, weekStart: Date, weekEnd: Date): number {
  const frameTime = new Date(frame.capturedAt).getTime();
  const start = weekStart.getTime();
  const end = weekEnd.getTime();
  return ((frameTime - start) / (end - start)) * 100;
}
```

#### Integration with PlotDetail

TimeLapsePlayer manages its own data fetching and week grouping. It does NOT share image state with PlotDetail. The week selector and play controls render inline below the hero image.

### 10.5 Error Handling

Phase D introduces new error conditions beyond the existing strategy (Section 4). These are specific to new flows.

#### 10.5a Map Tile Loading Failure

| Condition | Detection | User-Facing Behavior | Technical Detail |
|-----------|-----------|---------------------|------------------|
| Leaflet JS fails to load | `lazy(() => import('./MapPicker'))` catch | Fallback: 3 text inputs (latitude, longitude, elevation) with helper text "Enter your farm coordinates manually." | Leaflet is ~40KB gzipped. On slow connections or CSP issues, the dynamic import may fail. The wizard Step 2 detects the error boundary and renders the fallback form. |
| Map tiles fail to load (offline) | Leaflet `tileerror` event | Banner above map: "Map unavailable offline. Enter coordinates manually." Manual inputs appear below. | OpenStreetMap tile CDN may be unreachable. Map container renders but shows gray squares. |
| GPS denied | `navigator.geolocation` PermissionDeniedError | Toast: "Location access denied. Tap the map to set manually." GPS button returns to default state. | Non-blocking -- map still usable via manual pan/tap. |

#### 10.5b Elevation API Timeout

| Condition | Detection | User-Facing Behavior | Technical Detail |
|-----------|-----------|---------------------|------------------|
| Open-Meteo timeout (> 3s) | `AbortController` with 3s timeout | Elevation field shows "-- m" with editable text input. Wizard "Next" button still enabled (elevation is optional). | `fetch` with `signal: AbortSignal.timeout(3000)`. |
| Open-Meteo HTTP error | Non-200 response | Same as timeout. | Catches 4xx/5xx. No retry -- user can enter manually. |
| Open-Meteo returns invalid data | Missing `elevation` array in response | Same as timeout. | Defensive parsing: `response?.elevation?.[0]` with fallback. |

#### 10.5c Grid Resize with Existing Data

| Condition | Detection | User-Facing Behavior | Technical Detail |
|-----------|-----------|---------------------|------------------|
| Shrink removes empty beds only | Backend checks: no images/crops on beds being removed | Grid resizes. Removed beds are soft-deleted. Success toast. | Beds outside new bounds marked `status: 'inactive'`. Images preserved in DynamoDB under `BED#` PK. |
| Shrink would remove beds with crops | Backend checks: occupied beds in removed area | Confirmation dialog: "Removing rows will delete {N} beds with crops. Continue?" If confirmed, beds soft-deleted. If declined, resize canceled. | API returns 409 CONFLICT with `affected_beds[]` listing bed names and crop types. Frontend renders the confirmation dialog from this data. |
| Shrink would remove beds with images | Same as above | Same confirmation flow. Dialog adds: "{M} images will be archived." | Images remain in S3 and DynamoDB. Only the bed metadata is soft-deleted. Images are still accessible via direct URL. |

#### 10.5d Crop Assignment Validation

| Condition | Detection | User-Facing Behavior | Technical Detail |
|-----------|-----------|---------------------|------------------|
| crop_type empty | Frontend validation (required field) | "Save Crop" button disabled. No error message needed (field is visually required). | Zod schema: `crop_type: z.string().min(1).max(100)` |
| crop_type too long (> 100 chars) | Backend Zod validation | 400 VALIDATION_ERROR. Toast: "Crop type must be 100 characters or less." | Only reachable if "Other" freeform input is used. |
| notes too long (> 500 chars) | Backend Zod validation | 400 VALIDATION_ERROR. Toast: "Notes must be 500 characters or less." | Frontend also enforces `maxlength="500"`. |
| planted_at in future | Frontend validation (soft warning) | Warning text below date input: "This date is in the future." Submission still allowed. | Not a hard error -- pre-planting scheduling is valid. |
| Bed not found | Backend lookup miss | 404 NOT_FOUND. Toast: "Bed not found. It may have been removed." Sheet closes, grid reloads. | Possible if grid was resized by another session between opening the sheet and saving. |
| Unauthorized (observer role) | Middleware role check | 403 FORBIDDEN. Toast: "You don't have permission to assign crops." | CropAssignment sheet is hidden for observers via progressive disclosure, so this is a defense-in-depth catch. |

```typescript
/**
 * Device key verification middleware.
 * Extracts X-Device-Key header, looks up device by ID,
 * compares key via bcrypt. Uses dummy hash when device
 * not found to prevent timing side-channel.
 */
export async function verifyDeviceKey(
  deviceId: string,
  headerKey: string,
): Promise<{ valid: boolean; device?: Device }> {
  const device = await db.getDeviceById(deviceId);

  // Timing-safe: always compare, even if device not found
  const hashToCompare = device?.device_api_key_hash ?? DUMMY_BCRYPT_HASH;
  const valid = await bcrypt.compare(headerKey, hashToCompare);

  return { valid: valid && !!device, device: device ?? undefined };
}
```

```typescript
export const CreateDiaryEntrySchema = z.object({
  date: z.string()
    .regex(/^\d{4}-\d{2}-\d{2}$/, 'Date must be YYYY-MM-DD')
    .refine(s => !isNaN(Date.parse(s)), { message: 'Invalid calendar date' })
    .refine(s => {
      const y = parseInt(s.slice(0, 4), 10);
      return y >= 2020 && y <= 2100;
    }, { message: 'Date year must be between 2020 and 2100' }),
  category: DiaryCategorySchema,
  entry_type: DiaryEntryTypeSchema.optional().default('actual'),
  description: z.string().min(1).max(1000).trim(),
  time_spent_minutes: z.number().int().min(1).max(1440).nullable().optional(),
  bed_id: z.string().uuid().nullable().optional(),
  photo_ids: z.array(z.string().uuid()).max(5).default([]),
  costs: z.array(CostItemSchema).max(10).default([]),
  // -- Beta-10: Harvest & revenue fields --
  harvest_amount: z.number().min(0).max(999_999).nullable().optional(),
  harvest_unit: z.string().min(1).max(20).trim().nullable().optional(),
  revenue: z.number().min(0).max(99_999_999).nullable().optional(),
  revenue_currency: z.enum(['JPY', 'USD']).nullable().optional(),
}).refine(data => {
  // Harvest/revenue fields must be null/undefined when category is not 'harvesting'
  if (data.category !== 'harvesting') {
    const hasHarvestFields =
      (data.harvest_amount != null) ||
      (data.harvest_unit != null) ||
      (data.revenue != null) ||
      (data.revenue_currency != null);
    return !hasHarvestFields;
  }
  return true;
}, {
  message: 'Harvest and revenue fields are only allowed when category is harvesting',
  path: ['category'],
});
```

```typescript
// packages/shared/src/schemas/index.ts — UpdateDiaryEntrySchema

  .omit({ date: true })

  .refine(data => {
    // If category is being changed to non-harvesting, harvest fields must not be set
    // If category is not provided, skip this check (existing value used)
    if (data.category && data.category !== 'harvesting') {
      const hasHarvestFields =
        (data.harvest_amount != null) ||
        (data.harvest_unit != null) ||
        (data.revenue != null) ||
```

applying `.omit().partial()`, then re-apply the refine. If `.innerType()` is not
available in the project's Zod version, use a shared base object extracted from the
create schema.

```typescript
async createDiaryEntry(
  farmId: string,
  entryId: string,
  data: {
    date: string;
    category: DiaryCategory;
    entry_type: DiaryEntryType;
    description: string;
    time_spent_minutes: number | null;

    updated_at: now,
```

#### 12.4.2 Currency Filtering Helper

```typescript
/**
 * Sum costs from a single diary entry, filtered to the target currency.
 * Returns 0 if no cost items match the currency.
 *
 * IMPORTANT: This sums raw costs[] items, NOT the pre-computed cost_total,
 * because cost_total mixes currencies (see ARCHITECTURE.md 15.3).
 */
function sumCostsByCurrency(
  entry: DiaryEntryResponse,
  currency: 'JPY' | 'USD',
): number {
  return entry.costs
    .filter(c => c.currency === currency)
    .reduce((sum, c) => sum + c.amount, 0);
}

/**
 * Get revenue for an entry if it matches the target currency.
 * Returns 0 if revenue_currency does not match or revenue is null.
 */
function getRevenueByCurrency(
  entry: DiaryEntryResponse,
  currency: 'JPY' | 'USD',
): number {
  if (entry.revenue == null) return 0;
  if (entry.revenue_currency !== currency) return 0;
  return entry.revenue;
}

/**
 * Check if an entry has any financial data in a non-target currency.
 * Used to count excluded entries for the UI warning.
 */
function hasOtherCurrencyData(
  entry: DiaryEntryResponse,
  currency: 'JPY' | 'USD',
): boolean {
  const hasOtherCosts = entry.costs.some(c => c.currency !== currency && c.amount > 0);
  const hasOtherRevenue = entry.revenue != null &&
    entry.revenue > 0 &&
    entry.revenue_currency !== currency;
  return hasOtherCosts || hasOtherRevenue;
}
```

#### 12.4.3 computeRoi()

```typescript
/**
 * Compute farm-wide ROI summary for a set of diary entries.
 *
 * @param entries - Diary entries (already filtered to date range)
 * @param currency - Farm default currency for aggregation
 * @returns RoiSummary with totals filtered to the specified currency
 *
 * Edge cases:
 *   - Zero entries: all zeros, roi_percent = null
 *   - Zero costs, positive revenue: roi_percent = null (display "No costs")
 *   - Zero costs, zero revenue: roi_percent = null
 *   - Positive costs, zero revenue: roi_percent = -100
 *   - Mixed currencies: only target currency counted; excluded_entry_count > 0
 */
export function computeRoi(
  entries: DiaryEntryResponse[],
  currency: 'JPY' | 'USD',
): RoiSummary {
  let total_cost = 0;
  let total_revenue = 0;
  let harvest_count = 0;
  let excluded_entry_count = 0;

  for (const entry of entries) {
    total_cost += sumCostsByCurrency(entry, currency);
    total_revenue += getRevenueByCurrency(entry, currency);

    if (entry.category === 'harvesting') {
      harvest_count++;
    }

    if (hasOtherCurrencyData(entry, currency)) {
      excluded_entry_count++;
    }
  }

  let roi_percent: number | null = null;
  if (total_cost > 0) {
    roi_percent = Math.round(((total_revenue - total_cost) / total_cost) * 100);
  }
  // When total_cost === 0, roi_percent stays null regardless of revenue

  return {
    total_cost,
    total_revenue,
    roi_percent,
    entry_count: entries.length,
    harvest_count,
    excluded_entry_count,
  };
}
```

#### 12.4.4 computeRoiByBed()

```typescript
/**
 * Compute per-bed ROI breakdown.
 *
 * @param entries - All diary entries for the date range
 * @param beds - Farm bed list (for names and crop types)
 * @param currency - Farm default currency
 * @returns Array of BedRoiSummary, one per bed that has entries.
 *          Beds with zero entries are excluded.
 *
 * Entries with bed_id === null are grouped into a virtual "(no bed)" row.
 */
export function computeRoiByBed(
  entries: DiaryEntryResponse[],
  beds: FarmBedItem[],
  currency: 'JPY' | 'USD',
): BedRoiSummary[] {
  const bedMap = new Map(beds.map(b => [b.id, b]));

  // Group entries by bed_id (null → '__none__')
  const groups = new Map<string, DiaryEntryResponse[]>();
  for (const entry of entries) {
    const key = entry.bed_id ?? '__none__';
    const group = groups.get(key);
    if (group) {
      group.push(entry);
    } else {
      groups.set(key, [entry]);
    }
  }

  const results: BedRoiSummary[] = [];

  for (const [bedId, bedEntries] of groups) {
    const roi = computeRoi(bedEntries, currency);
    const bed = bedId !== '__none__' ? bedMap.get(bedId) : null;

    results.push({
      ...roi,
      bed_id: bedId,
      bed_name: bed?.name ?? (bedId === '__none__' ? '(no bed)' : '(deleted bed)'),
      crop_type: bed?.crop_type ?? null,
      crop_emoji: null,  // resolved by UI using getCropName()
    });
  }

  // Default sort: ROI descending (null ROI at the end)
  results.sort((a, b) => {
    if (a.roi_percent == null && b.roi_percent == null) return 0;
    if (a.roi_percent == null) return 1;
    if (b.roi_percent == null) return -1;
    return b.roi_percent - a.roi_percent;
  });

  return results;
}
```

#### 12.4.5 computeCostByCategory()

```typescript
/**
 * Compute cost totals grouped by diary category.
 *
 * @param entries - All diary entries for the date range
 * @param currency - Farm default currency
 * @returns Array of CategoryCostSummary sorted by total descending.
 *          Categories with zero cost are excluded.
 */
export function computeCostByCategory(
  entries: DiaryEntryResponse[],
  currency: 'JPY' | 'USD',
): CategoryCostSummary[] {
  const categoryMap = new Map<string, { total: number; count: number }>();

  for (const entry of entries) {
    const cost = sumCostsByCurrency(entry, currency);
    if (cost === 0) continue;

    const existing = categoryMap.get(entry.category);
    if (existing) {
      existing.total += cost;
      existing.count++;
    } else {
      categoryMap.set(entry.category, { total: cost, count: 1 });
    }
  }

  return Array.from(categoryMap.entries())
    .map(([category, data]) => ({ category, ...data }))
    .sort((a, b) => b.total - a.total);
}
```

#### 12.4.6 computeMonthlyTrend()

```typescript
/**
 * Compute monthly cost and revenue totals for a calendar year.
 *
 * @param entries - All diary entries for the date range
 * @param currency - Farm default currency
 * @returns Array of 12 MonthlyTrend objects (Jan-Dec), always 12 items.
 *          Months with no data have cost: 0, revenue: 0.
 */
export function computeMonthlyTrend(
  entries: DiaryEntryResponse[],
  currency: 'JPY' | 'USD',
): MonthlyTrend[] {
  // Pre-fill all 12 months
  const year = entries.length > 0
    ? parseInt(entries[0].date.slice(0, 4), 10)
    : new Date().getFullYear();

  const months: MonthlyTrend[] = Array.from({ length: 12 }, (_, i) => ({
    month: `${year}-${String(i + 1).padStart(2, '0')}`,
    cost: 0,
    revenue: 0,
  }));

  for (const entry of entries) {
    const monthIdx = parseInt(entry.date.slice(5, 7), 10) - 1;
    if (monthIdx < 0 || monthIdx > 11) continue;

    months[monthIdx].cost += sumCostsByCurrency(entry, currency);
    months[monthIdx].revenue += getRevenueByCurrency(entry, currency);
  }

  return months;
}
```

```typescript
  const [year, setYear] = useState(() => new Date().getFullYear());
  const [entries, setEntries] = useState<DiaryEntryResponse[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);
  const [defaultCurrency, setDefaultCurrency] = useState<'JPY' | 'USD'>('JPY');

  // Fetch farm to get default_currency
  useEffect(() => {
    getFarm(farmId).then(farm => {
      setDefaultCurrency(farm.default_currency ?? 'JPY');
    });
  }, [farmId]);

  // Fetch ALL entries for the selected year (auto-paginate)
  useEffect(() => {
    loadAllEntries();
  }, [farmId, year]);

  async function loadAllEntries() {
    setLoading(true);
    setError(null);
    const from = `${year}-01-01`;
    const to = `${year}-12-31`;
    const allEntries: DiaryEntryResponse[] = [];
    let cursor: string | undefined;

    try {
      do {
        const res = await getDiaryEntries(farmId, { from, to, limit: 100, cursor });
        allEntries.push(...res.data);
        cursor = res.meta.next_cursor ?? undefined;
      } while (cursor);

      setEntries(allEntries);
    } catch {
      setError(t('diary.error_loading'));
    } finally {
      setLoading(false);
    }
  }

  // Compute aggregates (memoized on entries + currency)
  const roi = useMemo(() => computeRoi(entries, defaultCurrency), [entries, defaultCurrency]);
  const roiByBed = useMemo(() => computeRoiByBed(entries, beds, defaultCurrency), [entries, beds, defaultCurrency]);
  const costByCategory = useMemo(() => computeCostByCategory(entries, defaultCurrency), [entries, defaultCurrency]);
  const monthlyTrend = useMemo(() => computeMonthlyTrend(entries, defaultCurrency), [entries, defaultCurrency]);

  // ... render year selector, summary cards, charts, table ...
}
```

#### 12.5.5 Auto-Pagination Strategy

The `loadAllEntries()` function above implements sequential pagination:

1. First request: `GET /farms/:farmId/diary?from=YYYY-01-01&to=YYYY-12-31&limit=100`
2. If `meta.next_cursor` exists, repeat with `&cursor=<value>`
3. Accumulate all entries into `allEntries` array
4. Set state once after all pages fetched

**Performance**: For a typical farm with 500-2000 entries/year:
- At 100 entries/page: 5-20 sequential API calls
- Each call is ~100-200ms (Lambda cold start is amortized after first)
- Total: 0.5-4 seconds. Acceptable for a dashboard that loads once.

**Loading UX**: Show skeleton loading state during fetch. The year selector
is interactive immediately (cancels in-flight fetches via AbortController).
