## 3. Implementation Strategy

### Single-Developer Workflow

#### Git Branching

```
main (production-ready, never direct push)
  └── develop (integration branch)
        ├── feature/infra-monorepo          ← Phase 0
        ├── feature/shared-types            ← Phase 1 (shared + infra tasks)
        ├── feature/api-core                ← Phase 2
        ├── feature/api-services            ← Phase 3 API track
        ├── feature/frontend-foundation     ← Phase 3 FE track
        ├── feature/scripts-setup           ← Phase 3 Scripts track
        ├── feature/frontend-screens        ← Phase 4 FE screens
        ├── feature/api-integration         ← Phase 4 API wiring
        ├── feature/simulator               ← Phase 4 Simulator
        ├── feature/polish-deploy           ← Phase 5
        └── ... (additional branches as needed)
```

**Branch strategy**: One feature branch per logical unit of work (often a phase-track combination). PR to `develop` when the branch's tasks are complete. Merge to `main` only at PoC completion with explicit user approval.

#### Commit Cadence

- **One conventional commit per completed task** (e.g., `feat(api): implement DynamoDB repository (T-API-03)`)
- **Intermediate commits** within large tasks are encouraged (e.g., `wip: DynamoDB query for farm hierarchy`)
- **Commit message format**: `<type>(<scope>): <description> (T-XXXX-NN)`
  - Types: `feat`, `fix`, `docs`, `refactor`, `chore`, `test`
  - Scopes: `infra`, `shared`, `api`, `frontend`, `sim`, `scripts`

#### Testing Approach by Phase

| Phase | Testing Level | What Gets Tested |
|-------|--------------|------------------|
| Phase 0 | Smoke | `npm install`, `tsc --noEmit` in each workspace |
| Phase 1 | Compile | TypeScript compilation across all workspaces, shared type imports |
| Phase 2 | Unit + Integration | DynamoDB repository queries against local/real table, S3 presigned URL generation, middleware chain, error handling |
| Phase 3 | Unit + API | Each API endpoint with seeded data (manual curl/httpie or simple test script), API client type correctness |
| Phase 4 | Integration + E2E | Frontend screens with live API, tagging flow end-to-end, simulator upload → dashboard visible |
| Phase 5 | E2E + Deployment | Full user journey (upload → view → tag → weather), deployment scripts to AWS, latency validation |

**Testing tools for PoC**:
- TypeScript compiler (`tsc --noEmit`) for type safety across workspaces
- Hono's built-in dev server for local API testing
- Manual browser testing for frontend (mobile viewport in DevTools)
- `curl` / `httpie` for API endpoint validation
- AWS CloudWatch for post-deployment verification

**Note**: Automated test suites (unit test framework, E2E framework) are intentionally lightweight for PoC. Test strategy will be formalized at MVP via `/cc-test`.

## 4. AWS Resource Provisioning Order

All resources are in **ap-northeast-1 (Tokyo)**. Reference: [PREREQUISITES.md](PREREQUISITES.md) §3.

### Pre-flight Checklist

Before starting Phase 2, confirm:

- [ ] AWS CLI v2 installed and configured (`aws configure --profile litcrop`)
- [ ] IAM user/role with permissions listed in PREREQUISITES.md §3
- [ ] Billing alert set at $5/month threshold
- [ ] Open-Meteo API reachable (`curl https://api.open-meteo.com/v1/forecast?latitude=36.03&longitude=138.26&current_weather=true`)
- [ ] LLM API key obtained (Anthropic or OpenAI) and stored in `.env` (not committed)

### Provisioning Sequence

Execute via `scripts/setup-aws.sh` (T-SCRIPT-02) or manually in this order:

```
Step 1: IAM Role
  └── litcrop-poc-lambda-role
        Policies: AmazonDynamoDBFullAccess (scoped to litcrop-poc table)
                  AmazonS3FullAccess (scoped to litcrop-poc-* buckets)
                  AWSLambdaBasicExecutionRole (CloudWatch Logs)

Step 2: DynamoDB Table
  └── litcrop-poc
        PK: pk (String), SK: sk (String)
        GSI1: GSI1PK (String) / GSI1SK (String)
        GSI2: GSI2PK (String) / GSI2SK (String)
        Billing: On-Demand (pay-per-request, free tier: 25 RCU/WCU perpetual)

Step 3: S3 Buckets
  ├── litcrop-poc-images
  │     Block all public access
  │     CORS: Allow GET from CloudFront origin
  │     Lifecycle: IA after 90 days (optional for PoC)
  └── litcrop-poc-static
        Block all public access (CloudFront OAI/OAC serves content)

Step 4: Lambda Function
  └── litcrop-poc-api
        Runtime: Node.js 20.x
        Memory: 256 MB (sufficient for image processing)
        Timeout: 30 seconds
        Role: litcrop-poc-lambda-role
        Environment: TABLE_NAME, IMAGE_BUCKET, LLM_API_PROVIDER, LLM_API_KEY

Step 5: API Gateway HTTP API
  └── litcrop-poc-api
        Protocol: HTTP (v2)
        Route: ANY /{proxy+} → Lambda integration
        CORS: Allow CloudFront origin, GET/POST/PATCH methods
        Stage: $default (auto-deploy)

Step 6: CloudFront Distribution
  └── Origin: litcrop-poc-static S3 bucket (OAC)
        Default root: index.html
        Error pages: 404 → /index.html (SPA fallback, though SSG mostly avoids this)
        HTTPS: Default CloudFront certificate (*.cloudfront.net)
        Price class: PriceClass_200 (Asia + US + EU)
```

### Provisioning Timeline

| Phase | What Gets Provisioned | When |
|-------|----------------------|------|
| Phase 2 (Day 3) | DynamoDB table (for local dev/testing) | Start of Phase 2 |
| Phase 3 (Day 5) | All AWS resources via T-SCRIPT-02 | Before first API deployment |
| Phase 3 (Day 5) | Seed data via T-SCRIPT-01 | After DynamoDB table exists |
| Phase 5 (Day 11) | First full deployment to AWS | Deploy scripts tested |

## 6. Risk Mitigation

### Risk Register with Schedule Placement

| # | Risk | Likelihood | Impact | Scheduled Phase | Mitigation Strategy |
|---|------|-----------|--------|-----------------|---------------------|
| R1 | DynamoDB single-table design doesn't support all access patterns | Medium | High | **Phase 2 (Day 3-4)** | Build T-API-03 first. Test all 9 access patterns with seed data (T-SCRIPT-01) before building services on top. If patterns fail, adjust PK/SK design while blast radius is minimal. |
| R2 | Lambda multipart image upload fails or hits size limits | Medium | High | **Phase 3 (Day 6)** | T-API-07 scheduled early in Phase 3. Test with real JPEG files (sample images from T-SIM-03). API Gateway HTTP API supports 10MB payloads; our 2MB limit is safe. Hono's `c.req.parseBody()` handles multipart. |
| R3 | Open-Meteo API response shape changes or is unreliable | Low | Medium | **Phase 3 (Day 6)** | T-API-09 builds weather proxy with 15-min cache. Stale data served as fallback if API is down. Transform layer isolates upstream changes. No API key dependency. |
| R4 | LLM API integration issues (prompt quality, cost, latency) | Medium | Low | **Phase 3 (Day 7)** | T-API-10 uses direct API calls (simplest approach). Start with minimal system prompt, iterate. LLM provider configurable via env var. Estimated cost well within budget ($0.05-0.50/month). |
| R5 | Farm Overview screen complexity exceeds single-task scope | Medium | Low | **Phase 4 (Day 8)** | T-FE-06 is the most complex screen. Build incrementally: tiles first → status bar → weather strip. Can defer weather strip to T-FE-10 integration if needed. |
| R6 | Plot Detail page with 4 Preact islands is too complex | Low | Low | **Phase 4 (Day 9)** | T-FE-08 can be split into sub-tasks if needed: HeroImage → TagButtons → ImageHistory → WeatherContext. Each island is independent. |
| R7 | AWS resource provisioning fails or permissions insufficient | Low | Medium | **Phase 3 (Day 5)** | T-SCRIPT-02 includes teardown option. IAM permissions documented in PREREQUISITES.md. Test with `--dry-run` where possible. |
| R8 | CloudFront + API Gateway CORS configuration issues | Medium | Low | **Phase 5 (Day 11)** | Different origins (CloudFront vs API Gateway). CORS headers configured in both API Gateway and Hono middleware. Test cross-origin requests from deployed frontend. |

### Risk-Ordered Implementation Sequence

The schedule front-loads the 5 highest-risk tasks identified in TASK-BREAKDOWN.md:

```
Day 3-4:  T-API-03 (DynamoDB repository)     ← Risk #1: Single-table design
Day 5:    T-SCRIPT-01 (Seed data)             ← Validates Risk #1 with real data
Day 6:    T-API-07 (Image upload)             ← Risk #2: Multipart in Lambda
Day 6:    T-API-09 (Weather proxy)            ← Risk #3: External API integration
Day 7:    T-API-10 (Chat route)               ← Risk #4: LLM integration
Day 8:    T-FE-06 (Farm Overview)             ← Risk #5: Complex screen
```

**Principle**: If any risk materializes, it does so early — leaving maximum time for course correction before Phase 4-5.
